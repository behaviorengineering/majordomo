# Typology cluster: mechanical walk vs RLM

*Decision note for context-digest clustering. Not PR file-batch clustering (`internal/cluster`).*

## Decision

**Structure is mechanical. Membership certainty is an RLM audit. CoT proposes; it does not self-certify.**

1. Walk from delivery doors (`entrypoint`, `server`) on the import graph.
2. Parse that reachability set with role stop signs into a cluster seed (door-private vs shared, product clumps, library candidates).
3. Ask `typology_cluster` CoT for an optional overlay: names, proposed folds, debt counsel, plus a structured `proposed_merges_yaml` field.
4. Run **one** `typology_cluster_audit` RLM Completes over the **full** proposed-merge list (not one call per row). The auditor is a challenger: `accept` | `overlay` | `reject` with why and evidence quotes. It MUST NOT invent a better map.
5. CoT revises only rejected rows (sticky by sorted package set, so a rename like `git` → `forge` cannot re-litigate). Unresolved rejects demote to teaching nicknames.
6. `typology_refine` may fold packages only when the verdict is `accept`. Overlay/reject stay separate package owners.

Roles (including post-RLM role validation) are brakes on ownership claims, not the grouping driver. The walk follows the programs; roles forbid bad merges (for example entrypoint with server, dto swallowed by an aggregator, exec_runner treated as CLI furniture).

## Why

A recursive language model shines when the model must **pull evidence on demand** across a large variable space (as with per-package role validation against AST context). Clustering’s first job is different: **reachability and shared-vs-private** are graph algorithms. Putting that walk inside RLM adds cost without clearer structure.

Theme merges (`localgit`+`remotegit` → `git`) can look fine to a counsel rubric while inventing catalog debt. Certainty must mean “survived evidence pushback,” not “another CoT liked the wording.” That is why Cluster RLM is the **auditor in the propose → audit → revise loop**, not the walk itself.

## Algorithm (target)

```text
package_roles + graph
  → doors = packages with role entrypoint | server
  → mechanical door-walk seed (private / shared / unreached)
  → typology_cluster CoT: propose merges + proposed_merges_yaml
  → typology_cluster_audit RLM: one pass over the full list
  → revise / sticky reject / demote overlays to nicknames
  → write cluster_merge_verdicts.yaml
  → typology_refine (fold only accept) → refined catalog YAML
```

Two doors never merge. Shared packages are not “won” by the first walk; they stay shared unless evidence says otherwise. Mechanical product clumps are seed hints only; a CoT merge still needs `accept`.

## What RLM still owns elsewhere

- **Package inspect RLM:** role validation against AST context (`typology_inspect`).
- **Slice ledger RLM:** evidence-first objectives (`typology_objective_grounding`).
- **Cluster audit RLM:** membership challenger over the full proposed-merge list (`typology_cluster_audit`). Not a second clusterer.

## Out of scope

- Replacing the mechanical door-walk with RLM
- Clustering as a pure series of RLMs with no CoT proposer
- Human-intervention / SliceBinding completion changes in this slice

## Status

Seed implemented in Typology `BuildMechanicalGrouping` door walks. Majordomo runs cluster CoT plus full-list Cluster RLM audit before refine. Counsel-only WeightedScore is no longer the merge pass gate.
