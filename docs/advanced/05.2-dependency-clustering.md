# Dependency Clustering

*Majordomo — repository operations for evolving software.*

Dependency clustering keeps related files together during review. The implementation is `scripts/dep_clusters.py`.

This page is for engineers understanding how `dep_clusters.py` groups changed files and computes reverse dependencies.

## 💡 Why Clustering Matters

If one changed file imports another changed file, reviewing them together reduces false confidence and improves correctness checks. Splitting tightly related files across distant batches increases the chance of missed regressions.

## ⚙️ How Clustering Works

### 1. Parse imports

The script parses import statements from Python and JS/TS (JavaScript/TypeScript) files and resolves relative imports to repository file paths.

It ignores package imports that do not map to repository files.

### 2. Build connected components

The script uses a union-find structure (a data structure that groups items into connected components efficiently). If changed file A imports changed file B, both files are unioned. Transitive relationships become one cluster.

### 3. Pack clusters into batches

Given a configured batch size, clusters are packed so related files stay adjacent.

Rules:

1. Large clusters are processed first.
2. Clusters are packed greedily.
3. Oversized clusters are split into consecutive sub-batches to preserve locality.

### 4. Compute reverse dependencies

The script scans unchanged repository files to find importers of changed files. This reverse dependency map feeds synthesis skills, especially blast-radius and summary.

## 📋 Typical Output Shape

The result contains two fields: `clusters` (a list of changed-file groups) and `reverse_deps` (a mapping from each changed file to the unchanged files that import it).

Example:

```json
{
  "src/auth/handler.py": ["src/api/main.py", "src/webhook/webhook.py"],
  "src/models/user.py": ["tests/test_auth.py"]
}
```

## 🔗 Where It Is Used

Staging uses the clustering output to create better batch plans. Dispatch and synthesis use the reverse dependency map to evaluate impact beyond the changed files.

## 📄 Doc Clustering

Doc clustering handles markdown files routed to `pr-review-docs`. The implementation is `scripts/doc_clusters.py`.

Unlike code clustering (which groups files by import relationships), doc clustering groups changed `.md` files by markdown link relationships and builds a full structural index of all docs in the repository.

### How It Works

1. **Parse markdown links** — The script scans each changed `.md` file for `[text](path.md)` links (both inline and reference-style) and resolves them to repository file paths.

2. **Build link clusters** — Changed docs that link to each other land in the same batch, using the same union-find structure as code clustering.

3. **Find reverse links** — The script scans all unchanged `.md` files to find which ones link to any changed file. This reverse link map feeds synthesis skills.

4. **Build corpus index** — `doc_clusters.py` walks every `.md` file in the repository and extracts title, H2/H3 headings, bold and backtick key terms, and outbound links. The result is written as `corpus-index.json` in the `pr-review-docs` batch directory.

### Corpus Index Shape

Each entry in `corpus-index.json` corresponds to one `.md` file in the repository:

```json
[
  {
    "file": "docs/02-setup.md",
    "title": "Setup Guide",
    "headings": ["Prerequisites", "Adding to Your Project"],
    "key_terms": ["git submodule", "pipeline branch", "webhook"],
    "links_out": ["docs/01-portable-pipeline-pattern.md"]
  }
]
```

The `pr-review-docs` skill uses this index to identify semantically related documents — by matching headings and key terms — without loading every file into context.
