## 🔍 Overview

This guide is for engineers operating the Jenkins PR review pipeline. It explains each runtime stage, the scripts each stage calls, and the artifacts each stage produces.

A Bitbucket webhook fires on `pr:opened` and `pr:from_ref_updated`. The pipeline runs inside a `Pipeline Guard` wrapper that deduplicates webhook events and enforces per-branch concurrency control. Inside that wrapper are nine named stages:

**Setup stages** (always run):
- Safe Checkout, Validate Config, Ensure Images

**Guard & Notify** (infrastructure):
- Pipeline Snapshot Guard (submodule drift check)
- Notify: Build In Progress (post to Bitbucket)

**Core work** (PR analysis):
- Static Analysis, PR Review

**Post-review** (reporting):
- Convert Reports to HTML, Publish PR Summary

Stage 2 (PR Review) is the core work: diff the PR, classify files by type, run Copilot agents over them in parallel, and aggregate findings. The agents score findings against rubrics until quality thresholds pass, then finalize a summary and technical review.

The post-review stages wrap up: convert reports to self-contained HTML and post the summary back to the PR.

Runtime branch model:

- Jenkins clones the app repo's pipeline branch (not master).
- The Jenkinsfile is pulled from the `.majordomo/` submodule branch; app repo master stays clean.
- Runtime config comes from `.majordomo-config.groovy` on the pipeline branch: project-specific settings like SonarQube and registries.
- For PR events, diff-sensitive stages switch to `CHANGE_BRANCH` before inspecting files.

**Important:** The `Pipeline Guard` stage uses a lock-based guard that skips inner stages on duplicate webhook events (e.g. when both `repo:refs_changed` and `pr:from_ref_updated` fire for the same commit). This is a feature, not a bug — it prevents duplicate reviews from consuming executor capacity.

## ⚙️ Pipeline Guard & Duplicate Detection

The top-level `Pipeline Guard` stage wraps all inner stages and implements duplicate-event detection + per-branch concurrency control.

**Problem it solves:** Bitbucket fires two events simultaneously for a push to an open PR:
1. `repo:refs_changed` (repository push)
2. `pr:from_ref_updated` (pull request source branch updated)

Without deduplication, the Jenkins job would run twice for the same commit, wasting executor capacity.

**Mechanism:**

```groovy
when {
    expression {
        def hasPr = isPrBuild()
        if (!hasPr) { return true }  // plain branch push — run normally
        def isNewPr         = params.PR_EVENT_TYPE == 'pr:opened'
        def triggeredByUser = currentBuild.getBuildCauses('hudson.model.Cause$UserIdCause').size() > 0
        def isRetrigger     = params.REPLAY_OF_BUILD?.trim() as Boolean  // fresh build queued by drift/replay handoff
        return isNewPr || triggeredByUser || isRetrigger
    }
}
```

Only three scenarios proceed past the guard:
- `pr:opened` events (new PR — always run)
- Manually triggered rebuilds by a user
- Fresh builds auto-queued by submodule drift (see Pipeline Snapshot Guard below)

All other events (duplicate `pr:from_ref_updated`, subsequent commits) skip the entire pipeline **before** any agent time is allocated.

**Concurrency:** Inside the guard, a per-branch lock ensures only one build runs per branch at a time, while different branches can run concurrently:

```groovy
lock(
    resource: "${env.JOB_NAME}-${params.CHANGE_BRANCH ?: params.PUSH_BRANCH ?: 'default'}",
    skipIfLocked: true
)
```

If a second event fires while the first is still running, the second build skips its inner stages instead of queuing — builds for other branches are unaffected.

## ⚙️ Pipeline Snapshot Guard

**Purpose:** Detect if the `.majordomo` submodule is behind the `updates` branch and offer a fresh-build handoff.

**Why it matters:** Pipeline code evolves on the submodule's `updates` branch. If your app repo's pipeline branch pins an old commit, you may be running stale pipeline code with bugs or missing features. This stage detects drift and pauses to let you opt in to a fresh build with updated code.

**How it works:**

1. Compare local commit SHA (checked out in the workspace) against remote `updates` branch
2. If they match: log and continue normally
3. If local is behind remote: 
   - Log a warning with the drift info
   - Present a **1-hour human-approval gate** asking whether to trigger a fresh build
   - If approved: automatically trigger a fresh build with `REPLAY_OF_BUILD` set (which bypasses the duplicate-detection guard, see above)
   - If not approved or timeout expires: fail the build with an error message directing the user to manually rebuild

**Important limitation:** This stage **blocks the pipeline** for up to 1 hour waiting for human input. If your submodule updates frequently, builds may accumulate in an approval queue or abort at the 1-hour timeout, consuming executor time.

**Recommendation:** Evaluate whether manual approval is necessary. Alternatively, configure the `gwtTokenCredentialsId` in `.majordomo-config.groovy` to enable automatic fresh-build triggering via webhook, which skips the 1-hour wait.

## ⚙️ Stage 2.1: Staging

### Skill categories

A skill is a `SKILL.md` file that gives the Copilot agent its review criteria, prioritisation tiers, and output format. Skills fall into two categories:

**File-review skills** - run per file and produce one `<slug>.md` report per changed file:
- `pr-review-code` - code quality, logic, security, and style findings for source files
- `pr-review-docs` - accuracy, completeness, and clarity findings for documentation and config files
- `pr-review-tests` - coverage gaps, assertion quality, and edge cases for test files

**Synthesis skills** - run once per PR across the full diff and produce whole-PR reports:
- `pr-review-summary` - human-readable summary of all changes: decisions, migration risks, deployment prerequisites, and business logic edge cases
- `pr-review-technical` - code correctness risks, architectural hazards, and verification questions for the engineer doing the deep diff review
- `pr-review-blast-radius` - what in the live repo is still coupled to the changed files, and whether it matters (only runs when reverse dependencies are present)

Each changed file routes to exactly one file-review skill. Synthesis skills work directly from the raw diff, so they do not wait for per-file reports. They run in round 1 alongside the first code batch.

`git-diff-prep.py` runs once at the start of every PR Review stage. It diffs changed files against the base branch, applies exclusion filters, classifies files by routing skill, embeds static analysis results, groups files by dependency cluster, and partitions them into batches (max 15 per batch). It produces three outputs:

| File | Contents |
|------|----------|
| `<staging>/manifest.json` | All changed files, their diffs, static analysis results, dep clusters, routing |
| `<staging>/batch-plan.json` | How to split the work: one entry per batch with skill, batch number, staging dir |
| `<staging>/<skill>/batch_NNN/` | One dir per batch, containing that batch's slice of the manifest |

### Task modes

The `mode` field controls how much of the file the agent sees. Files under 500 combined lines (content + diff) use `full_and_diff`. Files with a diff under 300 lines but large full content use `diff_only`. Larger diffs split into `diff_chunk` entries capped at 300 lines each, with SA (static analysis) findings appended to the final chunk only.

### Static analysis embedding

**Static analysis:** The Jenkins Static Analysis stage writes each tool's output to `.sa/<tool>.txt`. `git-diff-prep.py` scans every tool file for lines matching each reviewable file path and appends a `=== STATIC ANALYSIS ===` block to that file's staging input. The agent sees SA findings inline alongside the diff.

### Dependency clustering

**Dependency clusters:** `dep_clusters.py` parses Python `import`/`from` statements and JS/TS (JavaScript/TypeScript) `import`/`require` calls from every changed file. It builds a union-find graph: files that import each other land in the same component. When packing batches, `git-diff-prep.py` keeps files from the same cluster together, so the agent reviewing `controller.py` also sees `graph.py` if both changed and one imports the other.

## ⚙️ Stage 2.2: File review

`copilot-review.groovy` reads `batch-plan.json` and runs batches in parallel rounds.

Each batch calls `copilot-dispatch.sh` (mode=files), which:
1. Copies `manifest.json` + `SKILL.md` into `<staging>/<skill>/`
2. Rewrites `input_file` paths in the manifest to workspace-relative paths
3. Invokes the `copilot` CLI with `--agent=pr-review --autopilot`

The agent reads `SKILL.md` and the manifest, then reads each `input_file` and writes one `<slug>.md` report per file into `<output>/<skill>/`. Each report contains findings labeled `[CRITICAL]` (must fix before merge) or `[WARN]` (should fix). Finalize harvests these labels in the next step to build the findings digest.

The stage writes a checkpoint (`batch_NNN.done.txt`) to `<output>/<skill>/logs/` after each successful batch. If the PR Review stage is restarted in Jenkins (workspace preserved), the round loop checks for these files and skips already-completed batches.

## ⚙️ Stage 2.3: Finalize

A PR can produce hundreds of per-file reports; too large to pass to a single agent call. Finalize pre-filters them down to what matters before invoking the agent.

`copilot-dispatch.sh --finalize` runs once per file-review skill after all rounds complete. It pre-builds three files:

| File | Built by | Contents |
|------|----------|----------|
| `finalize-context.json` | `jq` from manifest | File list, counts, base branch (replaces the full manifest) |
| `findings.md` | `grep -rl [CRITICAL\|WARN] \| xargs cat` | Only reports that contain a `[CRITICAL]` or `[WARN]` finding, concatenated |
| `review_timestamp.txt` | `date` | Sydney-timezone timestamp |

The agent reads these three files (plus `SKILL.md`) and writes two outputs:

- `summary.md` - skill-level verdict (Approve / Request Changes / Needs Discussion), critical issues listed by file, and cross-cutting themes across the PR
- `index.md` - navigation page: links to every per-file report in priority order, with the excluded file list below

## ⚙️ Stage 2.4: Prose rewrite

`copilot-dispatch.sh --prose` runs once per file-review skill, after finalize and before synthesis. It rewrites all per-file reports in place, removing em dashes, label prefixes, hedging language, and other machine-prose patterns. Synthesis skills read the cleaned outputs.

The pass writes a checkpoint (`prose.done.txt`) on completion. A Jenkins stage restart skips the prose rewrite if this file is present.

## ⚙️ Stage 2.5: Synthesis

Two synthesis passes run in parallel after the prose rewrite, each with its own write → score → feedback loop.

**Summary** (`summary-loop.py`, up to 5 iterations, configurable via `SUMMARY_MAX_ITERATIONS`):
1. `build-all-diffs.py --cap 50` concatenates all diffs into `all-diffs.txt` (50 lines per file max)
2. `copilot-dispatch.sh --summary` reads `all-diffs.txt` and writes `summary.md`
3. `copilot-dispatch.sh --score` reads `summary.md` and writes `score.md` with `SCORE: N`. The Copilot agent scores against a rubric (max 23 points)
4. If score < threshold and iterations remain: write `score_feedback.md` and repeat from step 2
5. Best result is kept regardless of score if the cap is reached

Threshold defaults to 15/23, configurable via `SUMMARY_PASS_SCORE`.

**Technical** (`tech-review-loop.py`, up to 3 iterations, configurable via `TECH_MAX_ITERATIONS`):
1. `build-all-diffs.py` (no cap) concatenates full diffs into `all-diffs.txt`
2. `copilot-dispatch.sh --technical` reads `all-diffs.txt` and writes `tech-review.md`
3. `copilot-dispatch.sh --tech-score` reads `tech-review.md` and writes `tech-score.md` with `SCORE: N`. The Copilot agent scores against a rubric (max 14 points)
4. If score < threshold and iterations remain: write `tech_feedback.md` and repeat from step 2
5. Best result is kept regardless of score if the cap is reached

Threshold defaults to 11/14, configurable via `TECH_PASS_SCORE`.

## 📦 Convert Reports to HTML

`convert-reports.groovy` runs in a separate Jenkins stage after `PR Review`, inside the same Copilot CLI Docker image. It converts two Markdown reports to self-contained HTML pages and archives them as build artifacts:

| Report | Source | Artifact |
|--------|--------|----------|
| PR Summary | `pr-review/summary.md` | `pr-review/summary.html` |
| Technical Review | `pr-review/tech-review.md` | `pr-review/tech-review.html` |

Artifact URLs follow the pattern `${BUILD_URL}artifact/copilot-review-pr-{N}/pr-review/{report}.html`. Both files are self-contained, no external CSS or JavaScript.

## ⚙️ Stage 4: Publish

`review-to-junit.py` converts per-file finding reports to JUnit XML. Jenkins archives it as a build artifact.

`publish-pr-summary.py` posts `summary.md` to the Bitbucket PR as a description update or comment (configured via `auto` / `comment` / `description` mode).
