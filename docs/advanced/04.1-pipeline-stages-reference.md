## 🔍 Overview

This guide describes the PR review pipeline as **Go CLI + OpenCode**, orchestrated by the control tower (GitHub Actions). It explains each phase, what each phase calls, and the artifacts it produces.

A qualifying PR event (webhook or poll) triggers the control-tower workflow. The orchestrator checks out the PR branch, ensures agent/SA images exist, runs static analysis, executes the review inside the agent container, converts reports, and publishes back to the SCM.

**Phases:**

| Phase | Responsibility |
|-------|----------------|
| Prep | Checkout PR branch, validate config, ensure Docker images |
| Static analysis | Run SA tools; write `.sa/<tool>.txt` |
| Review | Staging → file review → finalize → prose → synthesis (via `majordomo orchestrate`) |
| Convert | `majordomo report html` for summary and tech reports |
| Publish | `majordomo report junit`, `majordomo publish` / `majordomo status` |

Stage 2 (Review) is the core work: diff the PR, classify files by type, run OpenCode agents in parallel, score findings against rubrics, then finalize summary and technical review.

**Runtime model:**

- Control tower holds org config (`majordomo-central-config/*.yaml`) and pins `.majordomo/` at a commit.
- Served app repos stay clean (no workflow files in default pull mode).
- For PR events, the orchestrator checks out `CHANGE_BRANCH` before diff-sensitive steps.
- Dedup and concurrency are handled by the workflow (`concurrency:` group) and poll reconciliation.

## ⚙️ Orchestrator concerns (dedup, drift, notify)

**Dedup:** GitHub Actions `concurrency: group: … cancel-in-progress` (or poll dedupe by repo + PR + head SHA) prevents duplicate reviews for the same commit.

**Submodule drift:** The control tower pins `.majordomo/` at an explicit commit. Bump the pointer in the tower repo to roll out pipeline changes — no in-job approval gate.

**Early notify:** Post INPROGRESS to the SCM (or create a pending check) before image build so auth failures still surface status. Use `majordomo status`.

## ⚙️ Stage 2.1: Staging

### Skill categories

A skill is a `SKILL.md` file that gives the OpenCode agent its review criteria, prioritisation tiers, and output format. Skills fall into two categories:

**File-review skills** - run per file and produce one `<slug>.md` report per changed file:
- `pr-review-code` - code quality, logic, security, and style findings for source files
- `pr-review-docs` - accuracy, completeness, and clarity findings for documentation and config files
- `pr-review-tests` - coverage gaps, assertion quality, and edge cases for test files

**Synthesis skills** - run once per PR across the full diff and produce whole-PR reports:
- `pr-review-summary` - human-readable summary of all changes: decisions, migration risks, deployment prerequisites, and business logic edge cases
- `pr-review-technical` - code correctness risks, architectural hazards, and verification questions for the engineer doing the deep diff review
- `pr-review-blast-radius` - what in the live repo is still coupled to the changed files, and whether it matters (only runs when reverse dependencies are present)

Each changed file routes to exactly one file-review skill. Synthesis skills work directly from the raw diff, so they do not wait for per-file reports. They run in round 1 alongside the first code batch.

`majordomo prep` runs once at the start of every PR Review stage. It diffs changed files against the base branch, applies exclusion filters, classifies files by routing skill, embeds static analysis results, groups files by dependency cluster, and partitions them into batches (max 15 per batch). It produces three outputs:

| File | Contents |
|------|----------|
| `<staging>/manifest.json` | All changed files, their diffs, static analysis results, dep clusters, routing |
| `<staging>/batch-plan.json` | How to split the work: one entry per batch with skill, batch number, staging dir |
| `<staging>/<skill>/batch_NNN/` | One dir per batch, containing that batch's slice of the manifest |

### Task modes

The `mode` field controls how much of the file the agent sees. Files under 500 combined lines (content + diff) use `full_and_diff`. Files with a diff under 300 lines but large full content use `diff_only`. Larger diffs split into `diff_chunk` entries capped at 300 lines each, with SA (static analysis) findings appended to the final chunk only.

### Static analysis embedding

**Static analysis:** The static-analysis phase writes each tool's output to `.sa/<tool>.txt`. `majordomo prep` scans every tool file for lines matching each reviewable file path and appends a `=== STATIC ANALYSIS ===` block to that file's staging input. The agent sees SA findings inline alongside the diff.

### Dependency clustering

**Dependency clusters:** `internal/cluster` parses Python `import`/`from` statements and JS/TS `import`/`require` calls from every changed file. It builds a union-find graph: files that import each other land in the same component. When packing batches, `majordomo prep` keeps files from the same cluster together, so the agent reviewing `controller.py` also sees `graph.py` if both changed and one imports the other.

## ⚙️ Stage 2.2: File review

The orchestrator reads `batch-plan.json` and runs batches in parallel rounds.

Each batch calls `agent-dispatch.sh` (file-review mode), which:
1. Copies `manifest.json` + `SKILL.md` into `<staging>/<skill>/`
2. Rewrites `input_file` paths in the manifest to workspace-relative paths
3. Invokes OpenCode (`opencode run --auto`) with the configured model

The agent reads `SKILL.md` and the manifest, then reads each `input_file` and writes one `<slug>.md` report per file into `<output>/<skill>/`. Each report contains findings labeled `[CRITICAL]` (must fix before merge) or `[WARN]` (should fix). Finalize harvests these labels in the next step to build the findings digest.

The orchestrator writes a checkpoint (`batch_NNN.done.txt`) to `<output>/<skill>/logs/` after each successful batch. On workflow retry with a preserved workspace, the round loop checks for these files and skips already-completed batches.

---

## ⚙️ Stage 2.3: Finalize

A PR can produce hundreds of per-file reports; too large to pass to a single agent call. Finalize pre-filters them down to what matters before invoking the agent.

`agent-dispatch.sh --finalize` runs once per file-review skill after all rounds complete. It pre-builds three files:

| File | Built by | Contents |
|------|----------|----------|
| `finalize-context.json` | `jq` from manifest | File list, counts, base branch (replaces the full manifest) |
| `findings.md` | `grep -rl [CRITICAL\|WARN] \| xargs cat` | Only reports that contain a `[CRITICAL]` or `[WARN]` finding, concatenated |
| `review_timestamp.txt` | `date` | Sydney-timezone timestamp |

The agent reads these three files (plus `SKILL.md`) and writes two outputs:

- `summary.md` - skill-level verdict (Approve / Request Changes / Needs Discussion), critical issues listed by file, and cross-cutting themes across the PR
- `index.md` - navigation page: links to every per-file report in priority order, with the excluded file list below

---

## ⚙️ Stage 2.4: Prose rewrite

`agent-dispatch.sh --prose` runs once per file-review skill, after finalize and before synthesis. It rewrites all per-file reports in place, removing em dashes, label prefixes, hedging language, and other machine-prose patterns. Synthesis skills read the cleaned outputs.

The pass writes a checkpoint (`prose.done.txt`) on completion. A workflow retry skips the prose rewrite if this file is present.

---

## ⚙️ Stage 2.5: Synthesis

Two synthesis passes run in parallel after the prose rewrite, each with its own write → score → feedback loop (Go code inside `majordomo orchestrate` / `internal/agent`).

**Summary** (up to 5 iterations, configurable via `SUMMARY_MAX_ITERATIONS`):
1. `majordomo report all-diffs --cap 50` concatenates diffs into `all-diffs.txt` (50 lines per file max; called from `agent-dispatch.sh` in summary mode)
2. `agent-dispatch.sh --summary` reads `all-diffs.txt` and writes `summary.md`
3. `agent-dispatch.sh --score` reads `summary.md` and writes `score.md` with `SCORE: N`
4. If score < threshold and iterations remain: write `score_feedback.md` and repeat from step 2
5. Best result is kept regardless of score if the cap is reached

Threshold defaults to 15/23, configurable via `SUMMARY_PASS_SCORE`.

**Technical** (up to 3 iterations, configurable via `TECH_MAX_ITERATIONS`):
1. `majordomo report all-diffs --cap 150` concatenates diffs into `all-diffs.txt` (technical mode)
2. `agent-dispatch.sh --technical` reads `all-diffs.txt` and writes `tech-review.md`
3. `agent-dispatch.sh --tech-score` reads `tech-review.md` and writes `tech-score.md` with `SCORE: N`
4. If score < threshold and iterations remain: write `tech_feedback.md` and repeat from step 2
5. Best result is kept regardless of score if the cap is reached

Threshold defaults to 11/14, configurable via `TECH_PASS_SCORE`.

**Technical deep (optional):** after tech-review, `majordomo orchestrate` runs a focused second pass on files cited in `tech-review.md` (`--skip-deep` to disable).

## 📦 Convert Reports to HTML

After review completes, convert Markdown reports to self-contained HTML:

| Report | Source | Command |
|--------|--------|---------|
| PR Summary | `pr-review/summary.md` | `majordomo report html …` |
| Technical Review | `pr-review/tech-review.md` | `majordomo report html …` |

Both files are self-contained — no external CSS or JavaScript.

---

## ⚙️ Stage 4: Publish

`majordomo report junit` converts per-file finding reports to JUnit XML for CI test reporting.

`majordomo publish --scm github|gitlab|bitbucket` posts `summary.md` to the PR (configured via `auto` / `comment` / `description` / Check mode). GitHub uses `gh`; GitLab uses `glab`; Bitbucket uses HTTP.

## 📋 Command map

**Ensure images**
- `pipelines/scripts/build-copilot-image.sh` — agent + SA tools + forge CLI images (`--target public|corp`)

**Review** (orchestrator host + agent container)
- `majordomo prep` — diff, classify, cluster, batch, write manifest (`internal/staging`, `internal/cluster`)
- `majordomo orchestrate` — waves, checkpoints, finalize/prose, summary/tech loops, tech-deep
- `majordomo dispatch` / `agent-dispatch.sh` — OpenCode for all modes
  - `majordomo report all-diffs` — concatenates diffs into `all-diffs.txt` for synthesis modes
- `pipelines/scripts/run-sa-tool.sh` — static analysis in SA containers

**Convert / publish / status**
- `majordomo report html` — Markdown → self-contained HTML
- `majordomo report junit` — findings → JUnit XML
- `majordomo publish` — post summary to SCM
- `majordomo status` — optional commit/check status

**Cache**
- `majordomo cache` — push, poll-cursor, precheck / lookup / store / restore

**Local tooling**
- `majordomo submodule` — manage a vendored `.majordomo` checkout
- `majordomo build-sa-tools` — local SA image smoke builds
- `majordomo poll` — control-tower poll reconciliation
